# API load test — local, 2026-11-07

**Setup:** one API process (Node 24, `tsx`), Postgres 18 / Meilisearch 1.56 / Valkey 9 in Docker Desktop on a laptop (8 CPUs, 8 GB), k6 also in Docker on the same machine. Full Tier A dataset (370,398 icons). No CDN, no cache in front — every request hits the origin. Script: [`load/api.js`](../../load/api.js) — mix of 35% search, 25% icon JSON, 30% customized SVG, 10% PNG render, random real queries/icons/colors/sizes.

Targets (uncached, [performance.md](../standards/performance.md)): search p95 ≤ 100 ms, icon JSON / SVG p95 ≤ 50 ms, PNG p95 ≤ 300 ms, errors < 0.1%.

## Results (after storing per-set icon counts)

| Load                     | Throughput | search p95 |   icon p95 |    svg p95 |    png p95 |     errors |
| ------------------------ | ---------: | ---------: | ---------: | ---------: | ---------: | ---------: |
| 10 VUs, 45 s (normal)    |  748 req/s | 20.3 ms ✅ | 17.5 ms ✅ | 17.9 ms ✅ | 22.9 ms ✅ | 0 / 33,646 |
| 50 VUs, 45 s (saturated) |  808 req/s | 57.5 ms ✅ | 87.8 ms ⚠️ | 86.8 ms ⚠️ | 91.4 ms ✅ | 0 / 36,395 |
| 50 VUs, 45 s (repeat)    |  843 req/s | 54.2 ms ✅ | 81.4 ms ⚠️ | 81.8 ms ⚠️ | 87.4 ms ✅ | 0 / 37,955 |

**Reading:** one process saturates at ~800–850 req/s; beyond that, latency is queueing, not slow code. At normal concurrency every target is met with a wide margin. Production runs ≥ 2 replicas behind Cloudflare, where most asset/metadata requests never reach the origin (target ≥ 90% cache hit ratio) — so the 50 ms targets apply per instance well below saturation.

## Findings fixed during the test

- **Per-request set counting.** Every icon request counted the icons of its set (up to 15k rows); `/v1/sets` counted all 194 sets (185 ms). Fixed by storing `icon_sets.icon_count` (migration 0002, maintained by the importer): `/v1/sets` 185 → 32 ms, throughput +30% (636 → 843 req/s).
- **Search outage returned 500.** During one run the whole Docker VM stalled (Meilisearch 5 s timeout, Valkey 500 ms timeout, k6 saw 28.6 s; 49/33,988 requests failed). Timeouts and the fail-open rate limiter behaved correctly, but search failures surfaced as 500. Now they return **503 + `Retry-After`** (graceful degradation). The stall did not reproduce in two repeat runs and is attributed to all services + k6 sharing one laptop VM.
